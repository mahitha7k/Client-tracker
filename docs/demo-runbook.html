This is Client Engagement Tracker — an internal tool for tracking client engagements and risk across active accounts. I built the API, the frontend, the cloud sign-in, and the deployment pipeline for it end to end.

1:00

Architecture, 30 seconds

The browser signs in with Microsoft, gets a token, and sends it on every API call. The API checks that token before it answers. Both the site and the API run as containers in Azure; the database is a managed MySQL server.

Trace the diagram above as you say it — left to right, then into the dashed box.

3:00

Live walkthrough

  1. Open the Web URL (see appendix) — point out it's already on HTTPS with a real Azure address, no custom setup.
  2. Click Sign in with Microsoft — you land on the actual Microsoft login page.
  3. Sign in. You're redirected straight back into the app, now showing the client list.
  4. Scroll the three seeded clients — Contoso Bank, Fabrikam Health, Northwind Retail — each with its engagements and a status badge (Active / Planned / On Hold).

This is real data returned from the API after a real login — nothing on this screen is mocked.

8:00

Prove the security is real

Open DevTools → Network tab, click the /api/clients request, show the Authorization: Bearer … header.

That token is what the API actually checks — this isn't just a login screen bolted on the front. If I strip the token out, watch what happens.

Switch to a terminal and run the curl command from the appendix — it comes back 401 Unauthorized.

The API refuses to answer anyone without a valid token, regardless of whether they know the URL.

11:00

Cloud infrastructure tour

Switch to the Azure Portal, resource group rg-clienttracker.

Two Container Apps (API + Web) — scale down when idle, so you only pay for what's used · a Container Registry holding the built images · a managed MySQL Flexible Server that Azure patches and backs up · the two Entra ID app registrations behind the sign-in.

13:00

How it ships

Both apps are Dockerized. Standing up the infrastructure and deploying new versions is two scripts — one for one-time setup, one for repeatable builds — so there's no manual clicking through the Portal and nothing that only exists in my head.

14:00

Wrap up

So: real cloud sign-in, an API that actually enforces it, and a deployment that's repeatable rather than one-off. Happy to go deeper into any piece — questions?

Security, in case it comes up

have these ready
✓ Standard, not homemade

OAuth 2.0 + PKCE

The browser never holds a client secret — it's the same auth-code flow banks and enterprise apps use for single-page apps.

✓ Least privilege

Two app registrations

The API and the website are registered separately in Entra ID, so the site only ever gets access scoped to this one API.

✓ Enforced server-side

The API checks, not just the UI

Every request is validated against the signed token and its scope inside the API itself — a hidden URL isn't a way in.

✓ Encrypted in transit

HTTPS end to end

Both apps are HTTPS-only, and the database connection requires TLS — nothing crosses the network in the clear.

Anticipated questions

answers to have ready
Is this production-ready?
The core patterns are: real OAuth, containerized services, a managed database. Before a real go-live I'd add monitoring/alerting, an automated CI/CD pipeline, and backup/disaster-recovery testing.
What does it cost to run?
Container Apps bills on consumption and the database is on the smallest Burstable tier — at this traffic level it's close to idle cost, and scales with actual usage.
What happens if the API crashes?
Azure Container Apps restarts unhealthy containers automatically and can scale out under load — no manual intervention.
How hard would it be to add a new feature, like Risks?
The database table and the API's repository layer for risks already exist — surfacing it in the UI is a contained, well-scoped addition, not a rebuild.
Why MySQL instead of SQL Server?
Matched to the schema this project started from. The data-access layer is written against a repository interface, not tied to MySQL specifically.
